# Архитектура

Один процесс Node.js обслуживает HTTP, запускает polling нового Telegram-бота и отправляет сообщения из постоянной очереди. Одна локальная SQLite хранит достоверное состояние. Фронтенд — HTML, CSS и JavaScript без сборки; сервер и бот используют общую модель предметной области. Внешних runtime-зависимостей нет.

## Компоненты

| Компонент | Назначение |
| --- | --- |
| `server.js` | HTTP API, сессии, пароли, CSRF, статические файлы и запуск бота |
| `lib/db.js` | Схема SQLite, начальные общие теги и настройки |
| `lib/domain.js` | Права, задачи, назначения, вопросы, история, пулы и постановка уведомлений в очередь |
| `lib/telegram.js` | Привязка, команды и кнопки бота, polling, обновление сообщений и повторная доставка |
| `public/` | Русскоязычный адаптивный веб-интерфейс; опрос API каждые четыре секунды |
| `test/` | Проверки модели, HTTP и Telegram с подменённым Bot API |

## Данные

| Сущность | Основные данные и связи |
| --- | --- |
| Пользователь | Совмещаемые роли, общие теги, основной холл, менеджер, независимая доступность, Telegram ID и chat ID |
| Общий тег | Имя, вид «холл»/«направление»; плоский список, управляемый администратором |
| Личный тег | Принадлежит менеджеру и связывается только с волонтёрами его пула |
| Публикация и задача | Общая группа публикации; отдельная задача на каждый выбранный холл, собственные статус и назначения |
| Назначение | Связь задачи и волонтёра; назначение и принятие хранятся отдельно |
| Вопрос и сообщение | Задача, инициатор, подтверждающий решение, адресные теги, срочность, блокировка, состояние обсуждения и история диалога |
| История задач | Автор действия, время, смена статуса/назначения, причины возврата или отмены и снимок прежнего выполнения |
| Общий журнал действий | Изменения пользователей, ролей, пулов, общих и личных тегов, доступности и настроек; тип и ID сущности, автор, время и данные до/после |
| Уведомление | Получатель и событие; совпадение нескольких тегов не создаёт дубликатов |
| Очередь доставки | Событие, пользователь, задача, состояние, число попыток, следующая попытка и последняя ошибка |
| Связанные сообщения | Telegram message ID, пользователь, задача и поколение назначения |
| Служебные данные | Сессии, ограничение попыток входа, одноразовые приглашения, обработанные update ID и callback ID, позиция polling и незавершённый ввод вопроса |

Статус задачи: `queued`, `in_progress`, `done`, `cancelled`. Признаки назначений, ожидания принятия, открытых вопросов и блокировки вычисляются отдельно. Основной статус не заменяется состоянием обсуждения. Блокировка сохраняется, пока открыт хотя бы один блокирующий вопрос; до его явного решения завершить задачу или снять назначения возвратом в свободную очередь нельзя. Отмена задачи остаётся отдельным действием.

## Согласованность

Изменения проходят через один слой бизнес-логики. SQLite `BEGIN IMMEDIATE` сериализует конфликтующие записи. Проверка текущего состояния, изменение, история и постановка исходящих событий выполняются в одной транзакции. Сетевые вызовы Telegram выполняются после неё, поэтому недоступность Telegram не теряет назначение.

Повторный `update_id` Telegram не исполняется заново. Отдельно сохраняются обработанные `callback_query.id`: повтор того же callback в другом update также не выполняет бизнес-действие ещё раз. Callback содержит идентификатор задачи и поколение назначения; возврат в очередь повышает поколение. Сервер проверяет актуальное назначение, поколение и конечный статус при каждом действии. Старые кнопки после завершения или смены исполнителей не изменяют задачу.

Очередь доставки сохраняется между перезапусками. Запросы обновления одной карточки объединяются, а уже взятое в отправку обновление помечается `processing`: изменение, пришедшее во время сетевого вызова, остаётся отдельным ожидающим запросом. После аварийного перезапуска незаконченная отправка восстанавливается. Обработчик отправляет актуальное состояние задачи, обновляет связанные сообщения, сохраняет ошибки и повторяет попытки с увеличивающейся задержкой. Ограничение Telegram `retry_after` при 429 приостанавливает всю исходящую очередь; успешно отправленные части длинного сообщения не повторяются при обычном ретрае. Перед следующей частью повторно проверяется доступ получателя; отозванная доставка отменяется. Менеджер видит недоставленные сообщения и может повторить отправку. В неоднозначном случае «Telegram принял сообщение, но ответ потерян» абсолютная гарантия одной сетевой отправки невозможна: повторная доставка может создать дополнительное сообщение, однако бизнес-действие остаётся идемпотентным.

## Доступ

Все веб-организаторы читают задачи общей очереди и очередей направлений. Менеджер начинает с очереди своего холла. Явно выбранный основной холл включается в общие теги пользователя; у прежней записи менеджера с единственным тегом холла основной холл выводится из этого тега. При нескольких холлах администратор должен явно выбрать основной; менеджер направления без холла использует общую очередь. Работа с чужими холлами проверяется сервером по административному флагу. Задачи без холла доступны для выполнения всем организаторам. Администратор управляет ролями, пулами, общими тегами, холлами и флагом.

Получатели вопроса определяются объединением пользователей с любым выбранным общим тегом, независимо от тегов исходной задачи. Первичный вопрос волонтёра доступен менеджеру; тот отвечает или передаёт его дальше. Неадресованные вопросы веб-пользователей и переданные без тегов вопросы находятся в общей отдельной очереди. Ответ переводит обсуждение в ожидание подтверждения решения. Закрывает его задавший вопрос организатор либо менеджер, которому поступил вопрос волонтёра, в том числе после передачи адресатам. Административная роль сама по себе не даёт права подтвердить решение чужого вопроса. Уточняющее сообщение инициатора переводит обсуждение обратно в ожидание ответа.

Возврат требует причины и доступен автору, текущему исполнителю, назначившему менеджеру или администратору с учётом доступа к холлу. Он снимает назначения и возвращает незавершённую задачу в очередь. Прежние исполнитель, назначивший менеджер и подтверждения назначенных волонтёров сохраняются в снимке истории. Изменение состава исполнителей выполняется через возврат и новое назначение. Завершённые задачи повторно не открываются.

Назначивший менеджер может при закрытии своего обсуждения явно выбрать передачу итогового пояснения всей текущей назначенной группе. Каждый участник получает одно итоговое сообщение; это не даёт ему доступа к частной истории вопроса или права ответа. Отложенная групповая доставка повторно проверяет назначение и поколение.

## Авторизация и подключение

Веб использует пароли и серверные сессии в HttpOnly cookies. Изменяющие запросы требуют CSRF-токен; вход ограничивается по попыткам. Повтор HTTP-запроса с тем же ключом не исполняет действие заново, но проверяет актуальные права. Операции с паролями и одноразовыми ссылками исключены из общего кэша ответов. Журнал действий не сохраняет пароли, токены, cookie или CSRF-материал. Для развёртывания за HTTPS включается Secure cookie и задаётся внешний origin.

Приглашение в Telegram содержит случайный одноразовый токен; в базе хранится его хеш и срок действия 24 часа. Привязка разрешена только из личного чата, проверяет Telegram ID и не заменяет уже привязанную личность. Волонтёр должен сам начать чат. Секрет бота хранится в окружении; в клиент и историю задач он не передаётся.

## Эксплуатация и границы проверки

Один процесс и одна локальная база подходят для координации одного мероприятия без микросервисов. Схема версии 2 добавляет журнал `activity` и дедупликацию callback, сохраняя бизнес-данные и историю; база с более новой версией отвергается до её изменения. Данные и история переживают перезапуск; резервное копирование описано в README. Изменения серверного JavaScript вступают в силу после перезапуска процесса; `npm start` не включает автоматическое перечитывание модулей. Для горизонтального масштабирования потребуется отдельное архитектурное решение — оно не добавлено заранее.

Автоматические проверки Telegram используют подмену транспорта. Доставку через настоящий Bot API нужно отдельно проверить с собственным токеном и добровольно подключённым тестовым пользователем. Старый бот изучен в зафиксированной ревизии: [технический разбор](legacy-review.md) содержит ссылки на прочитанные файлы и отделяет полезные сценарии от ограничений. Это справочное исследование не создаёт зависимости от прежнего кода, БД или запущенного процесса. Статус публикации и границы сетевых проверок описываются отдельно в отчёте аудита.
