# Архитектура

Один процесс Kotlin/JVM обслуживает HTTP, запускает polling нового Telegram-бота и отправляет сообщения из постоянной очереди. Одна локальная SQLite хранит достоверное состояние. Фронтенд — HTML, CSS и JavaScript без сборки; сервер и бот используют общую модель предметной области. SQLite подключается через JDBC, JSON обрабатывает Gson, Bouncy Castle проверяет совместимые с прежней версией scrypt-хеши.

## Компоненты

| Компонент | Назначение |
| --- | --- |
| `Server.kt` и `Api.kt` | HTTP, статические файлы, проверка формата запросов и маршрутизация |
| `Sessions.kt` и `RequestKeys.kt` | Вход, сессии, CSRF и повтор запросов с ключом идемпотентности |
| `Storage.kt` и `schema.sql` | SQLite, начальные данные, транзакции и вложенные точки отката |
| `Members.kt`, `Accounts.kt`, `VolunteerPool.kt` | Типизированные роли, учётные записи, права на пул и выбор волонтёров |
| `TaskWorkflow.kt`, `TaskQueries.kt`, `TaskRequests.kt` | Переходы состояния, выборки задач, обработка запросов и вычисление доступных действий |
| `Discussions.kt` | Состояния вопросов, адресация, история диалога и уведомления |
| `EventSettings.kt`, `DeliveryQueue.kt` | Общие теги, настройки мероприятия и операторская очередь доставки |
| `Telegram.kt`, `TelegramHttp.kt`, `TelegramUpdates.kt`, `TelegramOutbox.kt` | Polling, Bot API, привязка и команды, доставка и повтор по сохранённой очереди |
| `public/` | Русскоязычный адаптивный веб-интерфейс; опрос API каждые четыре секунды |
| `src/test/` | Проверки модели, HTTP и Telegram с подменённым Bot API |

## Данные

| Сущность | Основные данные и связи |
| --- | --- |
| Пользователь | Совмещаемые роли, общие теги, основной холл, менеджер, независимая доступность, Telegram ID и chat ID |
| Общий тег | Имя, вид «холл»/«направление»; плоский список, управляемый администратором |
| Личный тег | Принадлежит менеджеру и связывается только с волонтёрами его пула |
| Публикация и задача | Общая группа публикации; отдельная задача на каждый выбранный холл, собственные статус и назначения |
| Назначение | Связь задачи и волонтёра; назначение и принятие хранятся отдельно |
| Вопрос и сообщение | Задача, инициатор, подтверждающий решение, адресные теги, срочность, блокировка, состояние обсуждения и история диалога |
| История | Автор действия, время, смена статуса/назначения и причины возврата или отмены |
| Уведомление | Получатель и событие; совпадение нескольких тегов не создаёт дубликатов |
| Очередь доставки | Событие, пользователь, задача, состояние, число попыток, следующая попытка и последняя ошибка |
| Связанные сообщения | Telegram message ID, пользователь, задача и поколение назначения |
| Служебные данные | Сессии, ограничение попыток входа, одноразовые приглашения, обработанные update ID, позиция polling и незавершённый ввод вопроса |

Статус задачи: `queued`, `in_progress`, `done`, `cancelled`. Признаки назначений, ожидания принятия, открытых вопросов и блокировки вычисляются отдельно. Основной статус не заменяется состоянием обсуждения. Блокировка сохраняется, пока открыт хотя бы один блокирующий вопрос.

## Согласованность

Изменения проходят через один слой бизнес-логики. SQLite `BEGIN IMMEDIATE` сериализует конфликтующие записи. Проверка текущего состояния, изменение, история и постановка исходящих событий выполняются в одной транзакции. Сетевые вызовы Telegram выполняются после неё, поэтому недоступность Telegram не теряет назначение.

Позиция polling Telegram сохраняется в одной транзакции с обработкой `update_id`. Вложенные операции используют точки отката. Повторный `update_id` Telegram не исполняется заново. Callback содержит идентификатор задачи и поколение назначения; возврат в очередь повышает поколение. Сервер проверяет актуальное назначение, поколение и конечный статус при каждом действии. Старые кнопки после завершения или смены исполнителей не изменяют задачу.

Очередь доставки сохраняется между перезапусками. После подтверждения части длинного сообщения отправитель сохраняет её позицию в очереди. Обработчик отправляет актуальное состояние задачи, обновляет связанные сообщения, сохраняет ошибки и повторяет попытки с увеличивающейся задержкой. Менеджер видит недоставленные сообщения и может повторить отправку. В неоднозначном случае «Telegram принял сообщение, но ответ потерян» абсолютная гарантия одной сетевой отправки невозможна: повторная доставка может создать дополнительное сообщение, однако бизнес-действие остаётся идемпотентным.

## Доступ

Все веб-организаторы читают задачи общей очереди и очередей направлений. Менеджер начинает с очереди своего холла. Работа с чужими холлами проверяется сервером по административному флагу. Задачи без холла доступны для выполнения всем организаторам. Администратор управляет ролями, пулами, общими тегами, холлами и флагом.

Получатели вопроса определяются объединением пользователей с любым выбранным общим тегом, независимо от тегов исходной задачи. Первичный вопрос волонтёра доступен менеджеру; тот отвечает или передаёт его дальше. Неадресованные вопросы веб-пользователей и переданные без тегов вопросы находятся в общей отдельной очереди. Ответ переводит обсуждение в ожидание подтверждения решения; закрывает его инициатор либо передавший менеджер, а также администратор.

Возврат требует причины и доступен автору, текущему исполнителю, назначившему менеджеру или администратору с учётом доступа к холлу. Он снимает назначения и возвращает незавершённую задачу в очередь. Изменение состава исполнителей выполняется через возврат и новое назначение. Завершённые задачи повторно не открываются.

## Авторизация и подключение

Веб использует пароли и серверные сессии в HttpOnly cookies. Изменяющие запросы требуют CSRF-токен. Вход ограничивается по попыткам; при входе scrypt выполняется вне блокировки SQLite, а перед выдачей сессии проверяются актуальные данные участника. Активных волонтёров нужно переназначить до отключения их менеджера или снятия его роли. Для развёртывания за HTTPS включается Secure cookie и задаётся внешний origin.

Приглашение в Telegram содержит случайный одноразовый токен; в базе хранится его хеш и срок действия 24 часа. Привязка разрешена только из личного чата, проверяет Telegram ID и не заменяет уже привязанную личность. Волонтёр должен сам начать чат. Секрет бота хранится в окружении; в клиент и историю задач он не передаётся.

## Эксплуатация и границы проверки

Один процесс и одна локальная база подходят для координации одного мероприятия без микросервисов. Данные и история переживают перезапуск; резервное копирование описано в README. Для горизонтального масштабирования потребуется отдельное архитектурное решение — оно не добавлено заранее.

Автоматические проверки Telegram используют подмену транспорта. Доставку через настоящий Bot API нужно отдельно проверить с собственным токеном и добровольно подключённым тестовым пользователем. Исследование файлов старого бота и публикация исходников на GitHub в среде разработки заблокированы доступом и не считаются завершёнными.
