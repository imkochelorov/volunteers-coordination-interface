# Аудит NERC / volunteers-coordination-interface

Дата: 15 ноября 2026 года. Проверена вся кодовая база, включая существующие незакоммиченные изменения NERC и редактора холлов. Проверки выполнялись с временными базами; рабочие `.env`, SQLite и настоящий Telegram не использовались.

## 1. Источник требований и границы результата

Файла с точным названием `ТЗ` нет ни в checkout, ни среди файлов папки Neerc. Найден и полностью прочитан сохранённый текст **Pasted text(1).txt**, версия 0, 386 строк. Он содержит исходную спецификацию и все 26 сценариев раздела 10. При сверке также учтены последующие согласованные уточнения из диалога: общая видимость задач организаторам, задачи без тегов, общая очередь неадресованных вопросов, независимое выполнение публикации в каждом выбранном холле, возврат с причиной и управление холлами администратором.

**Вывод:** обнаруженные в проверенных сценариях ошибки устранены и закреплены регрессиями. Это не доказательство отсутствия любых возможных ошибок. **137/137 автоматических тестов проходят: 50 доменных, 23 HTTP, 26 Telegram, 3 дополнительные доменные/бот-регрессии E2E, 29 UI и 6 стресс-проверок; ошибок, предупреждений и пропусков в финальном прогоне нет.** Исходный набор содержал 38 тестов; добавлено 99. Доменные, HTTP-handler, Telegram-adapter, UI-unit, конкурентные и аварийные проверки пройдены. **Реальный браузерный проход выполнен через HTTP на изолированном стенде 4338, запущенном пользователем.** Telegram-события проходят настоящий адаптер, подменён только сетевой Bot API. Shell-доступ к TCP и Unix socket по-прежнему ограничен средой, поэтому сетевой конкурентный benchmark отдельно не выполнен. Его не заменяют замеры обработчика в памяти.

Старый бот фактически изучен через доступный GitHub connector в ревизии `9f9fdb2c371ac9c46649f00a136b252c9f94cf32`. Проверенные ссылки на модели, команды, авторизацию, хранилище, рассылку, тесты и workflow находятся в [техническом разборе](legacy-review.md). Старый репозиторий не изменялся и не запускался.

## 2. Архитектурный аудит

- Источник истины — одна SQLite. Веб и Telegram вызывают один `Domain`; бизнес-переходы не дублируются в адаптерах.
- Задачи, назначения, вопросы, история и исходящая доставка фиксируются транзакционно. Telegram вызывается вне бизнес-транзакции.
- Старые классы, команды, БД и работающий экземпляр прежнего бота для запуска не нужны. Все тестовые экземпляры создаются с новой базой.
- Основных статусов ровно четыре. Блокировка и ожидания вычисляются из отдельных назначений/обсуждений; состояние вопроса не подменяет статус задачи.
- Общие и личные теги разделены. Личные теги принадлежат менеджеру. Лишняя роль «ответственный за выполнение» отсутствует.
- Права проверяются сервером и повторно при HTTP replay, Telegram callback и отложенной доставке.
- Основные подписи, ошибки и статусы русские. Заданные ТЗ имена тегов и команды Telegram оставлены как данные/идентификаторы.
- Дополнен общий журнал `activity`; история задач сохраняет снимки прежнего исполнения. Секреты в журналы не записываются.
- Схема версии 2 добавляется без сброса бизнес-данных. Инициализация схемы, тегов и настроек атомарна; неизвестная будущая версия БД отвергается без понижения.

Подробная модель и протоколы: [architecture.md](architecture.md). Дополнительных файлов стандартов кодирования/AGENTS.md внутри репозитория не найдено; сохранены существующие модули и запуск без внешних npm-зависимостей. Массовый косметический рефакторинг не выполнялся.

Каждый перечисленный класс ошибок проверен воспроизведением или отрицательной регрессией. Исправлялась реализация; ожидания не ослаблялись ради прохождения тестов.

## 4. Проверка всех 26 сценариев раздела 10

Обозначения: D — настоящий домен/SQLite; H — настоящий HTTP-обработчик через потоки в памяти; T — рабочий Telegram-адаптер с подменённым Bot API; U — реальный код UI с подменёнными DOM/fetch на unit-границе; S — нагрузка/реальные Worker-потоки/аварийный процесс. **Все строки имеют автоматическую проверку на указанных слоях.** Дополнительный браузерный проход описан ниже; настоящий Bot API не подразумевается.

| --- | --- | --- | --- |

### Фактический браузерный проход

Проверены вход/выход менеджеров Hall 1 и Hall 2 и администратора; основная и отдельные очереди, «Мои задачи», входящие, исходящие, вопросы волонтёров, общая очередь вопросов без тегов, пул, доставка, управление пользователями/пулами/направлениями, добавление и переименование холлов. Проверены поиск и фильтры статуса, тегов, назначений, открытых вопросов и блокировки. На экране 390 × 844 карточка с длинным URL помещается без горизонтального переполнения; после проверки размер восстановлен. В журнале браузера нет warning/error.

- Взятие задачи организатором сразу дало «В процессе», завершение — «Выполнена» и запись истории.
- Назначение двух волонтёров сохранило «В очереди» и ожидание принятия. Принятие первым изменило статус, завершение вторым завершило группу и обновило обе Telegram-карточки. Старое действие получило контролируемый отказ.
- Выбор личного тега вместе с ручным выбором дал 2 уникальных получателя. Предпросмотр «Все свободные» исключил занятого и недоступного. После завершения одной из двух задач первый волонтёр остался «Доступен · занят» с оставшейся задачей, второй стал свободен. Доступность переключалась через бот независимо от назначений. Личные теги отредактированы через веб.
- Вопрос из Telegram поступил менеджеру, был передан с блокировкой и срочностью TC + Hall 2; ответ пришёл в общий thread и исходящие менеджера. Ответ не снял блокировку. Дополнительно две блокирующие темы закрыты по очереди: первая не сняла вторую. Неблокирующий вопрос остался открытым после завершения задачи.
- Ответ менеджера доставлен исходному волонтёру; явно выбранное итоговое пояснение отправлено обоим участникам группы. Это не завершило задачу автоматически.
- Ошибка Bot API 403 отображалась в очереди доставки; три назначения сохранились. После восстановления транспорта и нажатия «Повторить» все три задания отправились.
- Выключенный флаг оставил Hall 2 в режиме просмотра. Включённый позволил назначить свой пул, вернуть задачу с причиной и взять самостоятельно. Повторное выключение убрало действия даже у уже взявшего задачу менеджера. Прямой обход API отдельно покрыт H-тестами.
- Публикация на Hall 1 + Hall 2 создала независимые задачи №11 и №12: после завершения первой вторая осталась в очереди.

Стенд был запущен до последних трёх небольших серверных исправлений (`canCancel/canReset` и контекст прямых сообщений). Эти изменения проверены отдельными автоматическими регрессиями, но не выдаются за проверенные в уже работающем процессе. Последняя статика с защитой смены сессии перезагружена и проверена обычной навигацией, выходом/входом и административным сохранением. Конкурентная HTTP-нагрузка и жёсткий перезапуск полного HTTP/polling-процесса в браузере не выполнялись.

### Нюансы правил, не скрытые в реализации

- Задачи без тегов разрешены; вопросы без тегов находятся в отдельной общей очереди без массовой рассылки.
- Холлы плоские. Публикация на несколько холлов создаёт независимые выполнения; завершение одного не завершает остальные.
- Переназначение выполняется через возврат с причиной. Новое поколение инвалидирует старые кнопки. Возврат с открытой блокировкой отклоняется, чтобы не сделать заблокированную задачу свободной. Отмена не закрывает обсуждения автоматически.
- Авторство и контролирующий вопрос участник сохраняются независимо от административных ролей. Администратор не подтверждает чужое решение вместо автора/передавшего менеджера.
- Home hall включён в общие теги. Для прежней однозначной записи менеджера допустим единственный hall-тег; при нескольких холлах требуется явный выбор. Менеджер направления без холла работает с общей очередью.
- Итог группе отправляется только по явному выбору назначившего менеджера. Это не открывает другим участникам частное обсуждение и право ответа в нём.

### Развёртывание

Исправления публикуются в рабочую ветку `codex/new-coordination-system` по отдельному указанию пользователя. Деплой и перезапуск рабочего сервиса не выполнялись. `npm start` не перечитывает импортированные серверные модули: работающий экземпляр 4330 нужно перезапустить после резервного копирования. Наличие новой статики в браузере не означает, что старый процесс уже использует исправленный сервер.

Поддерживается один процесс приложения/один polling worker и локальный диск SQLite WAL. Для мероприятия необходимы HTTPS reverse proxy, `SECURE_COOKIES=1`, правильный `PUBLIC_ORIGIN`, исходящий доступ к Bot API, резервные копии и наблюдение за очередью доставки. Ограничения частоты реального Telegram добавляют задержки к массовой рассылке; миллисекунды подменённого API на сеть не переносятся. Абсолютная exactly-once гарантия отправки сообщения невозможна при потере ответа после принятия сообщения Telegram; бизнес-действия остаются идемпотентными, обычные ретраи частей дедуплицируются.

Docker-сборка, реальные сетевые таймауты, длительный soak-test и настоящий Telegram не проверены. Их статус не заменён зелёными unit/in-memory тестами.
