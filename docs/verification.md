## Браузерный E2E

Пользователь запустил изолированный сервер на **http://127.0.0.1:4338/**. Браузерные действия выполнялись против этого работающего сервера через **настоящий HTTP**, а не через подменённый HTTP-обработчик. Telegram в этом стенде эмулируется: интерфейс `/__audit` передаёт события рабочему адаптеру бота, который обращается к подменённому Bot API.

Проверены роли менеджера Hall 1, менеджера Hall 2 и администратора:

- Основная очередь Hall 1, отдельная страница Hall 2, запрет работы при выключенном crossHall и разрешение назначения своего пула/самостоятельного принятия при включённом флаге. Проверены поиск и сочетания фильтров статуса, тега, назначений, открытых вопросов и блокировок.
- Самостоятельное принятие и завершение через веб; назначение группы со статусом «В очереди» → принятие через эмулятор Telegram → готовность другого участника → «Выполнена» в вебе и обновление обеих карточек бота. Повтор устаревшей кнопки отклоняется.
- Пересечение личного тега и ручного выбора даёт двух уникальных исполнителей; предпросмотр свободных исключает занятых и недоступных. Несколько назначений сохраняют занятость после завершения одного; доступность переключается через бот независимо.
- Вопрос волонтёра → менеджер → передача блокирующего вопроса TC и Hall 2 → ответ второго менеджера → явное закрытие первым. Ответ не снимал блокировку; закрытие одного из двух блокирующих обсуждений оставляло вторую блокировку. Проверены входящие, исходящие, волонтёрские и неадресованные вопросы, прямой ответ менеджера и явная доставка итогового пояснения группе.
- Эмуляция Telegram 403 отображается в доставке, назначение сохраняется, восстановление и повторная отправка работают. Проверены личные теги, административное добавление/переименование холлов.
- Публикация на два холла сохраняет независимость: выполнение Hall 1 стало «Выполнена», Hall 2 осталось «В очереди». На мобильной ширине 390 px, включая длинный URL, горизонтального переполнения не обнаружено.

Три последних серверных исправления — разделение `canReset`/`canCancel` и однозначные ID задачи/вопроса в подтверждении и прямых ответах Telegram — покрыты автоматическими регрессиями. Уже запущенный стенд не перезапускался после этих правок: Node не перечитывает импортированные серверные модули. Поэтому их новые серверные поля и тексты **не заявлены как повторно проверенные в живом процессе**. Последующие UI-исправления подхватываются после перезагрузки страницы; окончательная последовательность браузерных проверок указана в отчёте.

## Нагрузка и сохранность

[Машинные метрики](audit-metrics.json) получены на Node.js v26.5.0. Нагрузочные измерения относятся к настоящему HTTP-обработчику с потоками запросов в памяти, SQLite и подменённому Bot API; это **не замер реального TCP под нагрузкой**. Проверены 50 независимых Worker-потоков с одним файлом SQLite, SIGKILL дочернего процесса и повторное открытие БД. Сохранились назначения, вопросы, история, outbox и дедупликация; незавершённая транзакция откатилась.

## Воспроизведение

```sh
npm run check
npm test
npm run audit:stress -- --output /tmp/nerc-stress-audit.json
node scripts/audit-server.js --seed-check
```

Для отдельного браузерного стенда на обычном хосте:

```sh
npm run audit:server
```

Стенд: `http://127.0.0.1:4338/`, эмулятор Telegram: `/__audit`. Используются синтетические учётные записи, временная БД и подменённый Bot API. Рабочие `.env`, данные и бот не используются. Стенд намеренно создаёт новое наполнение при запуске и удаляет временную базу при обычной остановке.

## Что не подтверждено

- Нагрузочный runner через настоящий TCP; из среды агента исходящие локальные соединения и открытие TCP/Unix socket по-прежнему ограничены.
- Жёсткий перезапуск HTTP-сервиса с последующим сетевым переподключением: проверен процесс/SQLite, а не этот сетевой цикл.
- Доставка через настоящий Telegram, Docker-сборка/запуск и длительный soak-test.
- Отсутствие любых долгосрочных утечек памяти или сетевых соединений. Короткая проверка памяти не является таким доказательством.
