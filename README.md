# NERC — координация организаторов и волонтёров

Самостоятельное приложение: русскоязычный веб-интерфейс организаторов, сервер, SQLite и новый Telegram-бот волонтёров. Веб и бот используют одну бизнес-логику и одну базу данных. Старый бот и его база для запуска не нужны.

## Быстрый запуск

Нужен Node.js **24.2 или новее**; рекомендуется Node.js 26. Внешних npm-зависимостей нет.

```sh
cp .env.example .env
```

Укажите в `.env` собственный `ADMIN_PASSWORD` до первого запуска. Затем:

```sh
npm start
```

Откройте [http://127.0.0.1:4319](http://127.0.0.1:4319). Логин первоначального администратора — `admin`, пароль — заданный вами. Аккаунт создаётся только в новой базе. Изменение `ADMIN_PASSWORD` не меняет пароль существующего аккаунта; используйте смену пароля в приложении.

В новой базе нет демонстрационных пользователей и задач. Через административный раздел создайте организаторов, менеджеров и волонтёров; назначьте общие теги, основной холл менеджеров и менеджера каждого волонтёра. Роли можно совмещать. Пользователь только с ролью волонтёра не может входить в веб-интерфейс.

## Telegram

1. Создайте отдельного бота через [@BotFather](https://t.me/BotFather).
2. Запишите `TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_USERNAME` в `.env`, перезапустите приложение. Имя указывается без `@`.
3. В списке волонтёров создайте личную ссылку подключения и передайте её соответствующему человеку. Ссылка одноразовая, действует 24 часа; храните её как приглашение к конкретному аккаунту.
4. Волонтёр открывает ссылку в личном чате с ботом и нажимает **«Начать»**. До этого бот не может первым начать личную переписку. Привязка выполняется по Telegram ID, а не по изменяемому имени пользователя.

После подключения бот принимает задания, обновляет их состояние, принимает подтверждения и вопросы, доставляет ответы менеджера. Кнопка «Готово» одного назначенного волонтёра завершает всю групповую задачу. Ответ на вопрос не закрывает обсуждение и не снимает блокировку.

Команды волонтёра:

| Команда | Действие |
| --- | --- |
| `/start` | Подключение по личной ссылке |
| `/tasks [страница]` | Свои назначенные задачи, по 50 на страницу |
| `/questions` | Входящие вопросы по общим тегам |
| `/reply номер текст` | Ответ в адресованном обсуждении |
| `/available` | Отметить себя доступным |
| `/unavailable` | Отметить себя недоступным |
| `/cancel` | Отменить ввод вопроса |
| `/help` | Справка |

Бот использует long polling: публичный webhook и входящий доступ из Telegram не нужны. Серверу нужен исходящий HTTPS-доступ к `api.telegram.org`. Запускайте один экземпляр приложения для одной базы и одного токена. Если другой процесс получает обновления этого же бота или у бота остался webhook, остановите его и удалите webhook перед включением polling. Старый бот лучше оставить с отдельным токеном.

Без токена веб-приложение работает, но Telegram-доставка не запускается. Назначения при этом сохраняются. Ошибки доставки видны менеджеру и администратору; после устранения причины сообщение можно отправить повторно. После подключения волонтёра проверьте недоставленные назначения.

## Принятые правила

- Все организаторы читают общую очередь и очереди направлений. Основной экран менеджера показывает его холл, остальные холлы открываются отдельно.
- Задачи без холла доступны для выполнения всем организаторам. Работа с чужими холлами требует административного флага, проверяемого сервером.
- Общие теги плоские. При публикации на несколько холлов создаются связанные, но независимо выполняемые задачи. «Все холлы» включает существующие теги холлов на момент публикации.
- Задачи без тегов разрешены. Вопрос без адресных тегов попадает в общую очередь неадресованных вопросов веб-пользователей; рекомендуется выбрать направления. Первичный вопрос волонтёра получает только его менеджер.
- Вернуть незавершённую задачу в очередь могут автор, взявший её организатор, назначивший волонтёров менеджер или администратор с учётом доступа к холлу. Причина обязательна. Назначения снимаются, прежние кнопки бота перестают действовать. Для смены исполнителей используйте возврат и новое назначение.

Свободный волонтёр одновременно доступен и не имеет ни одной незавершённой назначенной задачи. Ожидающие принятия и заблокированные задачи учитываются в занятости. Ручное назначение занятым или недоступным людям разрешено с явным показом этих признаков.

## Управление холлами

Администратор открывает **«Редактировать холлы»** в навигации или из административного раздела. Можно добавить холл и изменить название существующего. Холлы автоматически появляются в очередях, форме создания задач и выборе основного холла пользователя. Переименование сохраняет идентификатор холла, задачи, назначения и историю.

## Настройка

| Переменная | Назначение |
| --- | --- |
| `ADMIN_LOGIN` | Логин первого администратора, по умолчанию `admin` |
| `ADMIN_PASSWORD` | Обязательный пароль при создании новой базы |
| `HOST` | Адрес прослушивания, по умолчанию `127.0.0.1` |
| `PORT` | Порт, по умолчанию `4319` |
| `DATABASE_PATH` | Путь SQLite, по умолчанию `./data/app.sqlite` |
| `TELEGRAM_BOT_TOKEN` | Токен нового бота; пустое значение отключает polling |
| `TELEGRAM_BOT_USERNAME` | Имя бота без `@`; требуется при включённом боте |
| `PUBLIC_ORIGIN` | Точный внешний origin, например `https://volunteers.example.org`, для проверки запросов за reverse proxy |
| `SECURE_COOKIES` | `1` для HTTPS-развёртывания; локально по HTTP оставьте `0` |

Для доступа с телефонов используйте сервер с HTTPS reverse proxy. Направьте его на локальный порт приложения, укажите внешний `PUBLIC_ORIGIN` и `SECURE_COOKIES=1`. Пароли и токен не добавляйте в Git. Доступы управляются администратором приложения; открытая регистрация отсутствует.

## Docker

Нужны Docker и Compose. После настройки `.env`:

```sh
docker compose up --build -d
docker compose logs -f app
```

Адрес тот же: [http://127.0.0.1:4319](http://127.0.0.1:4319). Порт опубликован только на loopback хоста. Данные находятся в постоянном томе `app-data`; `docker compose down` их сохраняет. Команда `docker compose down -v` удаляет том вместе с данными — не используйте её для обычной остановки.

Для обновления сохраните резервную копию, обновите исходники и повторите `docker compose up --build -d`. Приложение рассчитано на один процесс и локальную SQLite; не подключайте несколько реплик к общей базе через сетевую файловую систему.

## Резервное копирование

Для согласованной копии работающей базы используйте встроенный механизм резервного копирования SQLite:

```sh
npm run backup -- backups/event.sqlite
```

Для Docker:

```sh
docker compose exec app node scripts/backup.js /app/data/backup.sqlite
docker compose cp app:/app/data/backup.sqlite ./event-backup.sqlite
```

Перенесите полученный файл в защищённое место вне рабочего сервера. Для восстановления остановите приложение, сохраните текущий каталог данных, замените рабочий файл резервной копией в отдельном чистом каталоге без прежних `-wal`/`-shm` файлов и запустите снова. В Docker используйте тот же путь `/app/data/app.sqlite` и права пользователя `node`.

Альтернатива: остановить приложение, скопировать весь каталог `data` или содержимое Docker-тома и снова запустить. Не копируйте только `app.sqlite` у работающего сервера: свежие изменения могут находиться в WAL.

## Проверка

```sh
npm run check
npm test
```

Автоматические тесты проверяют серверную логику, права, конкурентные изменения, сохранность данных и обмен с Telegram через подменённый Bot API. HTTP-сценарии вызывают настоящий обработчик запросов приложения в памяти, с потоками JSON, cookies и CSRF-проверками; TCP-соединение в них не открывается. Они не подтверждают работу браузера, прослушивание порта или доставку через настоящий Telegram. Подробное покрытие 26 сценариев и ограничения приведены в [проверке результата](docs/verification.md).

Для проверки живой интеграции подключите собственного тестового волонтёра настоящей ссылкой и выполните цикл: назначение из веба → получение в Telegram → «Взять в работу» → обновление веба → «Готово» → обновление всех назначенных сообщений. Дополнительно задайте вопрос в боте, ответьте в вебе и проверьте доставку ответа. Затем проверьте ошибку доставки после блокировки бота и повторную отправку после разблокировки.

Веб-интерфейс обновляет данные опросом сервера каждые четыре секунды. Для проверки перезапуска создайте задачу и обсуждение, перезапустите приложение и убедитесь, что назначения, история и сообщения сохранились.

## Аудит, нагрузка и изолированный E2E

Полный результат, статус 26 сценариев и границы проверки: [отчёт аудита](docs/audit-report.md). Машинные метрики: [audit-metrics.json](docs/audit-metrics.json).

```sh
npm run check
npm test
npm run audit:stress -- --output /tmp/nerc-stress-audit.json
```

Нагрузка по умолчанию использует настоящий обработчик HTTP в памяти, SQLite, подменённый Bot API и отдельные временные базы. Это не TCP-замер. Также проверяются 50 настоящих потоков SQLite, жёсткий SIGKILL и повторные циклы освобождения памяти. Режим `--tcp` требует разрешения на прослушивание локального порта.

Для браузера на обычном хосте:

```sh
npm run audit:server
```

Стенд открывается на `http://127.0.0.1:4338`, эмулятор Telegram — `/__audit`. Он не читает `.env`, не открывает рабочую БД и не обращается к настоящему Telegram. Используется временная тестовая база: 201 синтетический волонтёр, 8 задач и 4 обсуждения. Логины: `audit-admin`, `audit-manager-1`, `audit-manager-2`, `audit-organizer`; общий **тестовый** пароль `isolated-audit-password-2026`. Обычная остановка удаляет временную базу. Не открывайте стенд наружу и не используйте его для рабочих данных.

Второй терминал может проверить настоящий HTTP против этого стенда. Ключ берётся из вывода именно запущенного тестового сервера:

```sh
node --expose-gc scripts/stress-audit.js --url http://127.0.0.1:4338 --audit-token КЛЮЧ_ТЕСТОВОГО_СТЕНДА --output /tmp/nerc-tcp-audit.json
```

Runner проверяет подпись изолированного стенда и эмулятор Telegram до любых нагрузочных изменений. Проверить наполнение без TCP можно командой `node scripts/audit-server.js --seed-check`.

Серверные изменения требуют перезапуска `npm start`. Перед обновлением сохраните резервную копию. При старте схема автоматически дополняется до версии 2 без сброса задач/истории; база с более новой версией отвергается. Возврат назначенной задачи в очередь и завершение недоступны, пока остаются открытые блокирующие вопросы. Закрытие подтверждает только задавший организатор или получивший вопрос менеджер. При закрытии назначивший менеджер может явно выбрать отправку итогового пояснения всей группе; закрытие обсуждения не завершает задачу.
